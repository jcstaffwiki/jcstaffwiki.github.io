J.C.STAFF资料库 作品JSON填写说明

本文用于说明 data\works 里的作品JSON应该怎么填写。

第一次填写：先复制第一节的完整模板，再按第三节保存文件和登记作品。
普通人员只需要 ["职称", "姓名"] 这种写法。第七节讲主要staff的两列，第九节讲分集列表。
有同名人物再看第八节；有机构成员、部门标题再看第十节；要加单集备注再看第十一节。
示例中的人名和链接用于演示，正式填写时请换成本作资料；总览列也按本作确定。
本说明中标有“json”的代码框，只复制框内内容，不把代码框边界或说明文字放进JSON文件。

本文中的“作品库”，指网页顶部导航里的“作品库”页面。
这个页面会把 data\works\index.json 里登记的作品读取出来，按年份和季度显示成一张张作品卡片。
data\works 文件夹是作品JSON文件存放的位置；网页上的“作品库”是读这些文件后生成的列表页面。

最重要的一句话：
凡是从官网、通稿、OP、ED、片尾、PV、访谈资料等来源抄来的名称表记，尤其是人名、公司名、团体名，除非已确认错误表记，否则请保留原文的汉字、假名、大小写和标点，不要翻译、不要简化、不要改汉字、不要自行补全。
人名有一项全站统一处理：人名本体中的空格全部删除，包括半角、全角空格等，例如“坂部 剛”填写为“坂部剛”。此规则同时适用于主要制作人员、详细制作人员及其他人员信息；公司名、团体名和括号备注仍按原表记保留。
职位名称按照单独的职位翻译映射表来写。
如果名称表记里有括号，例如“瀧川三智（REAL-T）”，直接照抄。网页会自动把括号内文字当作备注隔开显示，人物链接会指向括号外的名字“瀧川三智”。


一、可直接复制的基础模板

下面是一个基础模板。新建作品时，可以先复制它，再逐项改内容。
注意：JSON里不能写注释，真正放进 .json 文件时不要加入“说明文字”。

```json

  "slug": "作品slug",
  "seasonYear": 2026,
  "season": "冬",
  "title": "作品中文名",
  "title_original": "作品原名",
  "type": "TV",
  "sourceCategory": "漫改",
  "episodes": 12,
  "premiere": "2026.01.01",
  "links": {
    "official": "https://example.com",
    "twitter": "https://twitter.com/example",
    "bangumi": "https://bgm.tv/subject/000000",
    "moegirl": "https://zh.moegirl.org.cn/作品名",
    "seesaa": "https://seesaawiki.jp/example",
    "keyframe_staff_list": "https://keyframe-staff-list.com/",
    "sakugabooru": "https://www.sakugabooru.com/post?tags=example"
  },
  "cn_streaming": null,
  "copyright": "© COPYRIGHT",
  "production_info": {
    "main_staff_columns": [
      [
        ["监督", "监督名"],
        ["角色设计", "角色设计名"]
      ],
      [
        ["系列构成", "系列构成名"],
        ["动画制作", "J.C.STAFF"]
      ]
    ]
  },
  "detailed_staff": {
    "overview_headers": ["脚本", "分镜", "演出", "作画监督", "制作进行"],
    "episodes": [
      {
        "label": "第1话",
        "staff": [
          ["脚本", "脚本名"],
          ["分镜", "分镜名"],
          ["演出", "演出名"],

        ]
      }
    ]
  }
}

```

完整的特殊写法范例在仓库根目录：
示例作品JSON.txt
它的内容是一份合法JSON；可以另存为 .json 再修改。sample-work 是虚构示例，不要把它直接加入正式作品库。


二、JSON基础规则

1. JSON结构的符号必须使用英文符号
包括：
英文双引号 " "
英文冒号 :
英文逗号 ,
英文中括号 [ ]
英文大括号 { }

以上规则只针对JSON的结构符号。双引号包住的文字里，可以保留原表记的中文／日文标点，例如“怀疑为‘某人’”中的引号。
名称里的 ・、（）、& 等照原表记保留。文字里需要英文双引号时写成 \"；需要反斜杠时写成 \\。

2. 项名不能随便改
例如：
"slug"
"seasonYear"
"title"
"production_info"
"detailed_staff"

这些项名是前端代码固定读取的，不能改成别的名字。

3. 文字要加双引号，数字不要加
正确：
"title": "某作品"
"episodes": 12

错误：
"title": 某作品
"episodes": "12"   （能显示，但不推荐）

4. 逗号规则
同一个大括号或中括号里，只要后面还有下一项，当前项末尾就要加逗号。
最后一项后面不要加逗号。

正确：
"title": "某作品",
"type": "TV"

错误：
"title": "某作品"
"type": "TV"

错误：
"title": "某作品",
"type": "TV",

5. 空内容怎么写
没有资料时，可以删除可选项；必填的slug、年份季度、标题、形式等仍需填写。
还没整理分集名单时，可暂时不写detailed_staff；不要用其他集数的名单补空。
如果说明里要求没有内容时写 null，就写 null，不加引号。

正确：
"links": null

错误：
"links": "null"


三、文件位置与新增作品步骤

1. 每部作品一个 JSON 文件
作品文件放在：
data\works

例如：
data\works\现在的是哪一个多闻.json

2. slug 必须和文件名一致
如果文件名是：
现在的是哪一个多闻.json

那么 JSON 里必须写：
"slug": "现在的是哪一个多闻"

3. index.json 必须加入 slug
新增作品后，还要打开：
data\works\index.json

把新作品 slug 加进去，例如：
{
  "works": [
    "现在的是哪一个多闻",
    "新作品slug"
  ]
}

只有加入 index.json，作品库才会读取这部作品。

4. slug 命名建议
slug 不会直接显示在页面上，但会用于文件名、链接和封面匹配。
建议：
尽量短一点
最好用作品中文名或方便识别的名字
不要加空格
不要使用 / \ : * ? " < > | 这类文件名危险字符
同一部作品的 slug、JSON 文件名、封面文件名必须一致


四、封面图片规则

1. 封面放置位置
封面放在：
data\covers

2. 封面文件名
封面文件名必须和作品 slug 一致。

例如作品 slug 是：
"slug": "现在的是哪一个多闻"

封面可以命名为：
现在的是哪一个多闻.webp
现在的是哪一个多闻.jpg
现在的是哪一个多闻.png

3. 支持格式
支持：
.webp
.jpg
.png

推荐优先使用 .webp，因为体积更小，网页加载更快。

4. 图片比例
推荐竖版封面。
大致比例推荐 3:4 到 2:3 之间。
太横的图会被裁切或留空，看起来不适合作品卡片。

5. 图片大小
不需要放超高清原图。
建议单张封面控制在 200KB 到 500KB 左右。
如果图片特别重要、细节较多，也尽量不要超过 1MB。
以后作品越来越多，图片太大会明显拖慢网页。

6. 没有封面也能显示
如果没有找到封面，网页会显示渐变占位图，不会报错。
但正式作品建议尽量补封面。


五、基础信息字段说明

1. slug（必填）
作品的定位名。
必须和 JSON 文件名一致。
必须在 data\works\index.json 里登记。

示例：
"slug": "现在的是哪一个多闻"

2. seasonYear（必填）
作品在作品库里归入哪一年。
只写数字，不加引号。

示例：
"seasonYear": 2026

这项不一定必须机械等于 premiere 的年份。
如果你判断某作品应归入 2026 冬番，就填 2026。

3. season（必填）
作品在作品库里归入哪个季度。
只能填写：
"冬"
"春"
"夏"
"秋"

一般参考：
1月开播：冬
4月开播：春
7月开播：夏
10月开播：秋

如果遇到特殊播出时间，可以按本资料库自己的分类判断。

4. title（必填）
作品中文名。
显示在作品详情页大标题和作品卡片上。

中文名建议优先级：
中国大陆正版译名
中国大陆官方宣传译名
繁中官译转简体
原作小说、漫画、游戏等官方译名
常用社区译名

5. title_original（建议填写）
作品原名。
显示在详情页中文标题下方。
这里不是专指日本名，而是该动画原发行地区、原始官方使用的标题。

示例：
日本动画通常填写日文原名。
如果以后收录的作品原发行地区不是日本，就填写该地区官方原名。

请使用官方动画标题，不要自行翻译。

6. type（必填）
作品形式。
只能填写：
"TV"
"剧场版"
"OVA"
"OAD"
"WEB"
"MV"
"制作协力"
"其他"

说明：
如果 J.C.STAFF 是主制作，按作品本身形式填 TV、剧场版等。
如果 J.C.STAFF 负责某一整集、OP、ED、PV、CM、LIVE part 等完整段落的制作协力，且本站决定记录这一条，填 "制作协力"。
如果只是部分外包，例如一部分原画、第二原画、动画、仕上、背景、摄影等工作外包给 J.C.STAFF，不能算作本站作品条目的 "制作协力"。
简单说：必须是某一整段或某一整集交由 J.C.STAFF 制作协力，才作为 "制作协力" 条目记录。
"其他" 用于 CM、活动动画等不适合归入前面类型的情况。

7. sourceCategory（必填）
来源类型。
只能填写：
"轻改"
"漫改"
"游戏改"
"原创"
"其他"

8. episodes（通常填写）
作品集数。

已完结：
"episodes": 12

未完结：
"episodes": "更新中"

未开播：
"episodes": "未开播"

如果 type 是 "制作协力"，通常不填 episodes，改填 responsibility。

9. responsibility（制作协力时填写）
当 type 是 "制作协力" 时，用它写 J.C.STAFF 负责的内容。

示例：
"responsibility": "第7/8话・OP"

普通主制作作品通常不需要这一项。

10. premiere（建议填写）
首播日期。
显示在详情页基本信息里。
格式建议：
"2026.01.01"


请尽量按北京时间 24 小时制判断首播日期。

11. links
作品相关资料链接。
显示在详情页“相关链接”。

基础款固定键名有七个：
"official"：官方网站
"twitter"：推特
"bangumi"：Bangumi
"moegirl"：萌娘百科
"seesaa"：Seesaawiki
"keyframe_staff_list"：KeyFrame Staff List
"sakugabooru"：SAKUGABOORU

这七个链接在网页上的显示顺序是固定的：
官方网站
推特
Bangumi
萌娘百科
Seesaawiki
KeyFrame Staff List
SAKUGABOORU

填写时也建议按这个顺序往上填。
有哪个填哪个，缺哪个就删掉那一行。
只有这七个基础链接全都没有时，才考虑写：
"links": null

示例：
"links": {
  "official": "https://example.com",
  "twitter": "https://twitter.com/example",
  "bangumi": "https://bgm.tv/subject/000000",
  "moegirl": "https://zh.moegirl.org.cn/作品名",
  "seesaa": "https://seesaawiki.jp/example",
  "keyframe_staff_list": "https://keyframe-staff-list.com/",
  "sakugabooru": "https://www.sakugabooru.com/post?tags=example"
}

如果还想加入其他链接，也可以继续往后写。
额外链接会显示在七个基础链接后面。
额外链接的“键名”，就是 links 里面冒号左边的那段文字。
例如下面这行里，annict 就是键名：
"annict": "https://annict.com/works/0000"

固定的七个键名会被网页自动显示成中文或常用名。
额外链接没有自动翻译，网页会直接把键名显示成链接名。
所以额外链接的键名建议写得短一点、能看懂一点。

示例：
"links": {
  "official": "https://example.com",
  "twitter": "https://twitter.com/example",
  "bangumi": "https://bgm.tv/subject/000000",
  "moegirl": "https://zh.moegirl.org.cn/作品名",
  "seesaa": "https://seesaawiki.jp/example",
  "keyframe_staff_list": "https://keyframe-staff-list.com/",
  "sakugabooru": "https://www.sakugabooru.com/post?tags=example",
  "annict": "https://annict.com/works/0000"
}

链接必须以 http:// 或 https:// 开头。
推荐统一使用 https://。

12. cn_streaming
中国大陆地区正版流媒体链接。
显示在详情页“中国大陆正版”。

有正版平台时：
"cn_streaming": [
  { "title": "哔哩哔哩", "url": "https://www.bilibili.com/bangumi/play/xxxx" },
  { "title": "爱奇艺", "url": "https://www.iqiyi.com/xxxx.html" }
]

没有中国大陆正版流媒体时：
"cn_streaming": null

只填写中国大陆地区正版，不填港澳台、日本、欧美等地区平台。

13. copyright
版权标。
显示在详情页基本信息底部。
请按官方版权标原样填写。

示例：
"copyright": "©師走ゆき・白泉社／多聞くん今どっち！？製作委員会"


六、名称和职称怎样填

1. 名称按来源，职称按翻译表

人名、公司名、团体名保留来源中的汉字、假名、大小写和标点。
人名本体删除排版空格，例如“坂部 剛”写成“坂部剛”；公司名、团体名和括号备注中的空格保留。
不要自行把瀧改成泷、歩改成步，也不要把公司全称改成习惯用的简称。
“保留原表记”同样适用于笔名和英文署名。

职称先查项目的职称翻译表，再把确认后的译名写进JSON。
网页不会自动将日文职称翻译成中文。
表里没有的职称先在审核稿列为待定，由本站负责人确定，或按其明确授权定译；确认后同步翻译表。

已确认的常用写法：
動画 → 動画
動画検査 → 動画检查
デジタル動画 → 数码動画
デジタル動画検査 → 数码動画检查
動画協力 → 動画协力
CGアニメーション → CG动画
撮影 → 摄影
仕上げ → 上色
仕上げ協力 → 上色协力
クリーチャーモデリング → 生物建模
演出補佐 → 演出辅佐
3DBGモデリング → 3DBG建模
総作画監督補佐 → 总作画监督辅佐
アニメーション制作統括 → 动画制作统括
アニメーションプロデューサー → 动画制片人
3Dコンポジット → 3D合成
原画、第二原画、背景、3DLO、3DCG保持原表记写法。
其余职称仍以当前翻译表为准。

合并职称逐项翻译，保留分隔和整条职称。
例如“制作担当・設定制作・制作進行”写成“制作担当・设定制作・制作进行”。
不能为了让总览更短，删掉分集职称的一部分。

2. 来源本来带括号，直接保留

下面是一条staff，放进主要staff的某一列，或某集的staff数组：
```json
["编集", "瀧川三智（REAL-T）"]
```

网页显示姓名和括号备注，人物链接指向“瀧川三智”。
其他作品才有的括注，不补到本作。
这种来源自带的括号，与第十一节的单集表底备注是两种写法。


七、主要制作人员：收录范围和左右两列

这一部分在作品文件的production_info里填写，显示在作品详情的“主要制作人员”区域。
main_staff_columns是两列名单：第一个数组是左列，第二个数组是右列。
每一条普通署名用 ["职称", "姓名"]；多人或多个公司，用名称数组。

1. 先确定哪些资料可以收录

请综合本篇官网、官方通稿、PV和原片表记，核对章节及来源位置。
“在官网／通稿／PV的STAFF表里”，指该来源的制作人员清单。
同页的独立音乐介绍、通稿的主題歌情報、PV的单独歌曲介绍区，都要与STAFF表区分。

按以下规则整理：
（1）动画制作人员和已确认的常见音响／音乐项目，可以按来源补入。
（2）原作、作画、各类原案等原作相关职务，不放进主要staff，保留给商业信息。
（3）製作、企画、企画協力、チーフプロデューサー、プロデューサー等商业／制委会署名：
      若本篇官网、通稿或PV的实际STAFF表已列出，按已确认的收录要求处理；
      若这些STAFF表都没有，则不只凭OP、ED或片尾补入主要staff，留商业／制委会信息。
（4）动画制作统括、动画制片人等属于动画制作部人员。不能因为职称含“プロデューサー”，就当成上一项的商业署名。

音响／音乐项目另需注意：
• 官网、通稿或PV的实际STAFF表已经列出的项目，可以收录；音乐制片人这类商业职务除外。
• 上述STAFF表没有、但OP有的常见项目，如音响监督、音乐、音响制作，可以补入。其他项目结合职务性质和常见程度审核，不照搬OP里的全部音乐署名。
• 音乐制片人（音楽プロデューサー）留商业信息，不填主要staff。
• 主题歌必须在官网、通稿或PV的实际STAFF表中作为职务列出，才收录到主要staff。
  例如STAFF清单与监督、音乐并列写“主題歌：F/ACE”，满足这个条件。
  独立音乐栏目、歌曲公告、PV歌曲区及OP／ED单独歌曲画面不满足，不适用上一条OP常见项目补充规则。
• 来源只写“主題歌”时用“主题歌”；来源区分OP、ED时，按完整职称分别定译，不能只凭“主題歌”的映射自行合并。
  歌名、作词、作曲、编曲、歌曲制作等详细歌曲信息留商业信息。

审核稿应写清原职称、完整署名和具体来源位置。材料未取得、字形不清或译名未定时，先标待核。
完整左右列和待定项目经本站负责人核对后，再按确认结果填写。

2. 两列和分区怎么写

制作部人员放在分区空行下面，例如动画制作统括、动画制片人、制作担当、设定制作、制作desk、制作进行。
监督、设计、美术、摄影、色彩、CG、音响、音乐等主要项目，以及动画制作公司，放在上面。
从分集资料追加的其他统一staff，按已确认的分组安排在下部。
按职务性质分区，不因它出现于官网还是OP而改变位置。

先在第一节模板中找到"production_info":。
保留这个字段名、冒号及字段间的逗号，将冒号后面包含main_staff_columns的整个{...}替换为下面对象。
这里只展示production_info的值，不是整份作品文件；不要再套一层production_info：
```json
{
  "main_staff_columns": [
    [
      ["监督", "山田太郎"],
      ["角色设计・总作画监督", "佐藤花子"],
      "空行",
      ["动画制作统括", "制作太郎"]
    ],
    [
      ["系列构成", "脚本太郎"],
      ["动画制作", ["J.C.STAFF", "SMDE"]],
      "空行",
      ["动画制片人", ["制作太郎", "制作次郎"]]
    ]
  ]
}
```

上例每列前两条在上部，第三项是分区空行，第四条开始列制作部人员。
网页同一行对应左右列的同一项。需要对齐分区或某一对岗位时，在较短的一列适当补"空行"；文字自动换行不用手工补空行。
统一使用"空行"容易读。旧文件用"-"作为空行的写法仍支持。

3. 从分集名单补主要staff

只取“每集都有同一个名字”的交集，不足以证明某岗位稳定。
候选应为值得展示的负责岗位，并核对每集同一岗位的完整署名组是否一致。
一集是A，另一集是A、B，就不是固定A单人；固定A、B两人应保留两人。
同一人跨不同岗位参加每集，不等于固定担任同一职务。
合并职称可以逐职务比较稳定性，但分集原来的整条职称仍保留。
候选写入审核稿，经确认后补到主要staff。OP、ED是否参与比较，也应在审核稿说明。


八、名称显示和人物页面

通常只写姓名，网页就会链接到同名人物文件。
例如 ["演出", "山田太郎"] 默认对应 data/people/山田太郎.json。
人物文件名不含路径和.json的部分，叫人物slug。
它与作品文件的slug是两个不同用途的定位名。

1. 名字相同，但要链接到不同人物

网页显示的姓名仍按来源。需要指定页面时，可以把这个人的姓名字符串换成姓名对象。
下面是一条staff：
```json
["演出", { "name": "山田太郎", "slug": "山田太郎(演出)" }]
```

name是显示姓名；slug让链接对应 data/people/山田太郎(演出).json。
同一条里有两个完全同名的人时，分别指定，各自与姓名放在一起：
```json
["作画监督", [
  { "name": "山田太郎", "slug": "山田太郎(作监A)" },
  { "name": "山田太郎", "slug": "山田太郎(作监B)" }
]]
```

不需要指定页面的其他姓名仍用普通字符串。
同一个人在不同岗位出现，不等于不同人物；只有身份有依据时，才建立不同人物页面或合并别名。

2. 同一个人／公司有多个署名表记

保留每条署名的显示名，让它们指向同一个slug。
下面两条可分别放在主要staff或分集staff中：
```json
[
  ["动画制作", ["J.C.STAFF", "SMDE"]],
  ["音乐制作", "小学館ミュージック&デジタル エンタテイメント", {
    "小学館ミュージック&デジタル エンタテイメント": "SMDE"
  }]
]
```

第二条末尾的对象表示“显示名称 → 页面slug”。
两条中的SMDE公司署名均对应 data/people/SMDE.json，显示名称仍各按原表记。
这类条目末尾映射也能用于普通人名及机构成员。
确认过的同人／同机构关系才合并；怀疑线索使用第十一节的备注。

3. 页面文件和搜索别名

指定slug不会自动创建人物资料文件。
没有文件时，页面只显示暂无信息，标题可能使用刚点击的署名。
需要统一页面标题和搜索别名时，在data/people中准备对应文件。

下面是可单独保存为 data/people/SMDE.json 的页面格式示例：
```json
{
  "slug": "SMDE",
  "name": "SMDE",
  "name_jp": "株式会社小学館ミュージック＆デジタル エンタテイメント",
  "aliases": [
    "小学館ミュージック&デジタル エンタテイメント",
    "小学館ミュージック＆デジタル エンタテイメント",
    "ＳＭＤＥ"
  ],
  "bio": ""
}
```

页面已有文件时，在原文件上核对修改，不用示例覆盖已有履历。
name是页面名称；name_jp及aliases提供其他可搜索名称；bio是介绍。
aliases只补搜索，不自动改变staff链接。链接仍按姓名对象的slug或条目末尾映射指定。

人员搜索从已收录作品的staff建立名单，再读取页面别名。
只创建页面、没有任何作品署名，不会让它自动进入人员搜索。
本作同一页面的不同署名会汇总为一个人物／机构搜索结果。
搜索忽略英文字母大小写，但不自动互换全角／半角、空格或&／＆；有依据的不同写法可分别放入aliases。

4. 旧格式中的按名字／按位置映射

旧格式继续支持。按名字映射适合“同一条里不同名字”，例如：
```json
["制作进行", ["山田太郎", "hei", "制作花子"], {
  "山田太郎": "山田太郎(制作)"
}]
```

同一条里有两个完全同名的人时，名字映射无法区分，改用第1项的姓名对象，或下面的按位置映射：
```json
["第二原画", ["山田太郎", "hei", "山田太郎"], [
  "山田太郎(二原A)", "", "山田太郎(二原B)"
]]
```

后面的三个slug按顺序对应前面的三个署名；无需映射的位置也要用空字符串""占位。
机构也占一个映射位置，空行和部门标题不占。机构层级的具体例子见第十节。
姓名对象直接写的slug优先于条目末尾映射；link:false会关闭这些链接，见第十一节。


九、详细制作人员：分集、总览和去重

这一部分写在作品的detailed_staff中。
overview_headers决定总览的列；episodes是逐段名单。
这里的episodes与作品顶层的集数episodes不是同一项：
顶层 "episodes": 12 表示作品有12话；
detailed_staff里的episodes数组保存各话／OP／ED等制作名单。

1. 从一份完整分集结构开始

先在第一节模板中找到"detailed_staff":，它与production_info位于同一层。
保留这个字段名、冒号及字段间的逗号，将冒号后面的整个{...}替换为下面对象。
这里只展示detailed_staff的值，不是整份作品文件；不要再套一层detailed_staff：
```json
{
  "overview_headers": ["脚本", "分镜", "演出", "制作进行"],
  "episodes": [
    {
      "label": "第1话",
      "staff": [
        ["脚本", "脚本太郎"],
        ["分镜・演出", "演出太郎"],
        ["制作进行", "制作花子"]
      ]
    },
    {
      "label": "第2话",
      "staff": [
        ["脚本", "脚本次郎"],
        ["分镜", "演出次郎"],
        ["演出", "演出花子"],
        ["制作进行", ["制作太郎", "制作次郎"]]
      ]
    }
  ]
}
```

每段用一对{}，写label和staff；下一段加在episodes数组中，两段之间加逗号。
一条staff是一组[]，放在该段staff数组里，不放在episodes的外层。
label可以是OP、ED、第1话、第12话、LIVE part动画（第5话）等。
只填写本作品实际有的段落，按审核确认的顺序排列；本片没有独立OP／ED表就不建空段落。
材料尚未取得时在审核稿标缺，不填别集名单代替。
主要staff和分集staff使用相同的普通单人、多人和人物映射写法。

2. 总览怎样找到对应岗位

overview_headers里的列名按本作品确认，示例的四列不是固定要求。
姓名精对哪些岗位是另一次范围决定，每次单独确认，与总览列数无关。

网站会按完整职称中用“・”“·”或“/”隔开的各段匹配总览列。
例如上面的“分镜・演出”，会同时进入“分镜”和“演出”两列。
分集详情仍显示完整的“分镜・演出”，不会改成两条署名。

特殊职称需要归到某列时，在staff条目第3项写总览列名：
```json
["LIVE part制作进行", "制作太郎", "制作进行"]
```

本条在分集显示“LIVE part制作进行”，同时可进入总览的“制作进行”列。
目标列名要写进overview_headers；总览归类是补充匹配，不会禁用职称本来对应的其他列。
需要归到多列时，可在第3项写合并列名，例如"分镜・演出"。
职称的各段和指定归类都未匹配表头时，这条只在分集显示；总览没有对应署名时显示“-”。
总览不会根据主要staff自动补分集人员。

3. 职称保留与去重

完整分集职称先按翻译表映射，再照实保留。
搜索标签是否拆分，见第十二节；它不改变分集职称，也不影响总览归类。

从详细staff删除主要staff中的重复项目前，必须同时确认：
• 完整职称一致；
• 该岗位的整组署名一致，包括原来的机构分组，不能只看其中某个人；
• 主要staff没有为总结共同职务而拆分、截短、合并或改写该来源职称。

例如主要staff的CG制作进行署鄭ジウン、矢野達也，ED只署鄭ジウン，两组不同，ED条目保留。
同一个人在其他职称下的署名也保留，不能按名字整体删除。

合并职称在部分集数增加职务，主要staff又只总结其中共同部分时，相关各集都保留完整记录。
例如第1—3话写“制作担当・设定制作”，第4话写“制作担当・设定制作・制作进行”，四话照实保留。
第4话可按“制作进行”这一职务进入总览；第1—3话没有这个职务，不因同一人而补进那一列。
不能只留下第4话多出的“制作进行”，也不能把整个合并职称删掉。


十、机构成员、空行和部门标题

普通名称数组表示并列署名；原表记明确把人员列在机构下面时，才用studio和members。
以下写法可用于主要staff的某一列，也可用于某集的staff数组。
关系只代表本次署名分组，不直接证明人员长期在该机构任职。

1. 一个机构带多个人

下面是一条staff，机构之外的人仍放在机构对象之外：
```json
["原画", [
  {
    "studio": "J.C.STAFF作画部",
    "members": ["橋詰力", "田中愛美", "山下真子"]
  },
  "空行",
  "另列人员"
]]
```

studio写机构、部门或团体的原名称；members写它下面的人员，按原顺序排列。
网页显示机构名，其下缩进成员；然后空一段，再显示“另列人员”。
上例仅演示结构，成员完整名单仍以各集原表记为准。
成员属于哪一组，由members的范围决定，不能只靠空行或名字相邻来推断。

多个机构各带人员时，将各机构对象放在同一个名称数组中：
```json
["背景", [
  { "studio": "株式会社スタジオ・ユニ", "members": ["中島美枝子"] },
  "空行",
  { "studio": "Fusion Studio", "members": ["LEOWLEEWON"] }
]]
```

只有机构署名、没有列出成员时，直接写名称，不写空members：
```json
["上色协力", ["神龍", "Production I.G"]]
```

原表记确有更深一层机构时，members中还可以放机构成员对象。
机构和成员分别形成链接及人员搜索项；要关闭某位成员链接，可在members里使用第十一节的姓名对象。

2. 两种空行放置位置

同一职称里面的名称分隔：将"空行"放进名称数组。
```json
["原画", ["人员A", "空行", "人员B"]]
```

两条职称之间的分隔：将"空行"放进该列／该集的staff数组。
下面是一个完整段落，放进detailed_staff.episodes：
```json
{
  "label": "第1话",
  "staff": [
    ["原画", "人员A"],
    "空行",
    ["第二原画", "人员B"]
  ]
}
```

前一种在同一岗位里空一段，可出现在主要staff、分集及总览单元格。
后一种隔开整条岗位，显示在主要staff或分集，不生成总览行。
空行不算人名、机构或职称，不生成链接和搜索项。

3. 部门标题放在staff里单列

如果原表记是先写部门标题，下面再列不同职称，使用section。
下面是一个完整段落，放进detailed_staff.episodes：
```json
{
  "label": "第1话",
  "staff": [
    { "section": "J.C.STAFF作画部" },
    ["動画检查", "荻野信子"],
    ["動画", "福本帆風"],
    ["動画协力", "神龍"]
  ]
}
```

section只显示部门标题，不作为职称、不链接人物、不进入人员索引或职称统计。
标题不会自动将后面的神龍归为J.C.STAFF作画部的下属机构。
需要记录“机构 → 成员”的关系时，仍用studio、members，不用section代替。

4. 机构内同名人物的链接

最容易维护的写法，是直接在该成员身上指定slug：
```json
["原画", [
  {
    "studio": "机构A",
    "members": [
      { "name": "山田太郎", "slug": "山田太郎(机构A原画)" },
      "普通人员"
    ]
  },
  "空行",
  { "name": "山田太郎", "slug": "山田太郎(另列原画)" }
]]
```

机构本身需要指定页面，或沿用旧数据时，可使用第八节的条目末尾映射。
若使用按位置的slug数组，顺序是机构名、该机构内成员、下一个同级名称；嵌套机构按同样顺序展开。
例如：
```json
["原画", [
  { "studio": "机构A", "members": ["同名人员", "普通人员"] },
  "空行", "同名人员"
], ["", "同名人员A", "", "同名人员B"]]
```

四个位置依次是机构A、机构内同名人员、普通人员、机构外同名人员。
后面的映射必须有四项；不需映射的机构和普通人员也用""占位。空行不占位。


十一、单集表底备注：疑名、编号和返回

想对某次署名作说明时，把该人的姓名字符串换成姓名对象，在对象里写note。
note只用于详细staff的单集／独立OP／ED等段落；主要staff可以指定name、slug、link，但不写note。
资料不确定时保留原署名，备注写已知线索，不把怀疑人名替换成事实。

1. 先看一个完整段落

下面是本片第3话的备注格式示例。放进detailed_staff.episodes，或用其中的staff条目修改既有第3话；不要重复添加整个第3话：
```json
{
  "label": "第3话",
  "staff": [
    ["演出", {
      "name": "前園丈夫",
      "link": false,
      "note": ["怀疑为“", { "name": "前園文夫" }, "”"]
    }]
  ]
}
```

正文显示“演出：前園丈夫①”。前園丈夫使用普通正文颜色，没有底色，不能点击人物页。
单集表底显示“① 怀疑为‘前園文夫’”，其中前園文夫可点击其人物页。
这只是怀疑线索，不会将前園文夫算成本片已确认的演出署名。

姓名对象各项：
name：必填，原片实际署名；人名本体的排版空格仍删除。
link：可选，不写或写true时正常链接；写false时关闭这个姓名的链接。
slug：可选，指定对应的人物文件名；不写时按普通姓名和既有映射处理。
note：可选，该次署名的本集备注。写文字或下面这种由文字与姓名对象组成的数组。
true、false是布尔值，不加双引号。link:false优先于slug及条目末尾映射。

2. 常用的三种修改

只关链接，不加备注：
```json
["演出", { "name": "原片署名", "link": false }]
```

只有文字备注：
```json
["原画", {
  "name": "人员A",
  "note": "原片如此署名，身份尚待核对。"
}]
```

备注需要人物链接：普通文字写字符串，人物写姓名对象，按数组顺序拼接。
```json
["演出", {
  "name": "原片署名",
  "link": false,
  "note": [
    "可能是",
    { "name": "显示姓名", "slug": "人物文件slug" },
    "，尚待确认。"
  ]
}]
```

备注中的姓名对象也可以写link:false，但不再嵌套note。
不写HTML，也不手填①、②或返回位置。

多人或机构成员只改需要备注的那个人，其他姓名保持原写法：
```json
["原画", [
  {
    "studio": "机构A",
    "members": [
      "人员A",
      { "name": "人员B", "link": false, "note": "姓名待确认。" }
    ]
  },
  "空行",
  "另列人员"
]]
```

3. 编号和往返由网站自动完成

• 每个单集按完整staff中备注首次出现的顺序编号①、②、③……，下一集从①重新开始。
  实际存在的独立OP、ED等段落也各自编号。
• 同一集里相同显示姓名、相同链接身份及相同备注共用编号；不同内容另编号。
  超过20条时显示[21]、[22]等。
• 姓名与序号保持在一起，不将序号单独换行。
• 点正文序号，打开对应单集并跳到表底备注；手机端列表被折叠时自动展开。
  总览里的序号沿用那一集的编号，也会先打开对应单集。
• 再点底注序号，返回刚才的总览或单集，恢复滚动位置和折叠状态。
  打开备注中的人物页再返回作品，也保留这条返回路径。
  如果直接滚到备注、没有之前的跳转记录，底注序号定位到本集对应姓名。
• 没有note就不生成编号，没有备注的集数也不显示空备注区。

备注中的人名只用于说明和链接，不进入真实署名人数、岗位统计或人物补全。
link:false的原署名仍可按文字搜到所在作品，但不会自动成为可链接的人物或人物补全项。
姓名对象本身占一个署名位置；note里的姓名不占人物映射位置。
普通姓名、机构成员、空行、部门标题和原有映射都继续支持。


十二、常用写法速查和搜索标签

1. 一条staff的基本顺序

第1项：显示的完整职称。
第2项：一个名称、名称数组、姓名对象，或含机构成员的名称数组。
后面按需要增加：总览归类、人物映射、split_role设置。

基础写法不需要填后面的可选项。
下面几种都是单条staff。普通写法和人物映射可放进主要staff的一列或某集的staff数组；带note或总览归类的示例用于分集。

普通单人：
```json
["演出", "山田太郎"]
```

普通多人：
```json
["作画监督", ["人员A", "人员B"]]
```

同名人物加单集备注：
```json
["演出", {
  "name": "山田太郎",
  "slug": "山田太郎(演出)",
  "note": "按本片原署名保留。"
}]
```

上面的note示例仅放分集staff；主要staff只保留name和slug即可。

总览归类加人物映射：
```json
["特殊分镜", "山田太郎", "分镜", {
  "山田太郎": "山田太郎(特殊分镜)"
}]
```

总览归类加姓名对象：
```json
["特殊分镜", {
  "name": "山田太郎",
  "slug": "山田太郎(特殊分镜)"
}, "分镜"]
```

2. 搜索职称标签的split_role

默认情况下，作品库人员搜索结果和作品内“主要职务”标签，会按“・”“·”和“/”拆分职称。
例如“角色设计・总作画监督”分为“角色设计”和“总作画监督”标签。
主要staff正文、分集详情及按集列出的详细职务，仍显示原来的完整职称。

某条需要在搜索标签中保持完整职称时，在该staff最后加：
```json
["动作・特效作画监督", "武藤健", { "split_role": false }]
```

不写或写true都使用默认拆分；true、false不加引号。
这个设置只控制这一条的搜索标签，不控制总览，也不改变分集职称。
同一人其他来源单独署过的职称仍保留。
一条写了多人时，设置对该条所有人员生效；仅需一人特殊设置时，把其原署名另列一条，保持机构关系和来源分组。

可与归类及映射一起写。下面的示例放分集staff：
```json
["特殊原画・动作原画", [
  { "studio": "机构A", "members": ["山田太郎"] },
  "空行", "其他人员"
], "原画", {
  "山田太郎": "山田太郎(原画)"
}, { "split_role": false }]
```

第3项归到总览“原画”，第4项指定山田太郎的人物页，最后一项让搜索标签保留整条职称。
姓名对象中的slug、条目末尾人物映射和split_role分别负责不同功能，无需把设置塞到姓名或机构对象里。


十三、检查、常见错误和提交

1. 保存前先检查

• 文件名、内部slug和作品索引一致；封面与slug对应。
• 名称保留原字形；人名去排版空格，公司名和括注保留空格。
• 主要staff两列和分区对齐，分集完整职称及机构关系没有丢失。
• 总览表头按本作确定，分集数据有来源，去重按完整职称与整组署名。
• 页面映射有身份依据，目标文件和页面标题正确；疑名不擅自合并。
• 备注不用手填编号，note只出现在分集；中文标点放在字符串内部。

2. 用检查脚本核对格式

安装了Node.js后，在项目根目录打开终端，即能看到index.html、assets和data的那一层。
Windows、macOS及Linux均可使用下面的正斜杠路径：
```sh
node tools/check-data.js
```

它会检查作品索引、文件是否存在、slug、季度／形式／改编类型、链接写法、staff格式、机构成员、姓名对象、单集备注和映射数量；缺少封面会给提醒。
“错误”需要修正；“提醒”需核对，但不一定阻止显示。
脚本检查不了姓名是否正确、是否确为同一人、资料是否齐全、实际机构所属和收录取舍，这些仍须对照来源。
检查通过后，打开网页检查电脑与手机布局、人物链接、总览和备注往返。

只检查某份尚未合并的staff草稿时：
```sh
node tools/check-data.js --staff-only "详细staff草稿.json"
```

这个方式只检查main_staff_columns／detailed_staff的写法，不检查完整作品信息、索引或封面。
也可以用它检查另存后的格式示例：
```sh
node tools/check-data.js --staff-only "示例作品JSON.txt"
```

3. 常见误填

文件有了、作品库却不显示：核对data/works/index.json是否登记slug，再检查年份和季度。
JSON打不开：核对结构双引号、逗号和括号；最后一项不加逗号，文件里不写注释或代码框标记。
相同字段写两次：替换原来的production_info或detailed_staff，不把示例另贴成第二个同名字段。
页面仍未合并：aliases只是搜索名，还要指定staff链接slug；目标资料文件也要核对。
某个人被误归到机构下：检查姓名是在members里面还是机构对象外，不能只看空行。
只有部门标题，没有成员层级：section不建立所属；所属关系用studio和members。
note写在主要staff：移到对应分集；只需关链接时，主要staff可用link:false而不写note。
同组同名的位置映射错位：映射数必须等于实际署名数，含机构、排除空行；无映射的位置用""占位。
按位置维护困难时，直接给每个同名人物写姓名对象和slug，见第八节。

4. 推荐顺序

复制完整模板 → 改基础信息与slug → 保存作品文件 → 登记索引和封面 →
整理主要staff双列 → 按实际资料填写分集及本作总览列 →
按需补机构、映射或备注 → 运行检查 → 打开网页确认。

只有基础信息和主要staff时可以先录入，分集以后补。
本说明介绍已经支持的数据写法；一部作品没有某段，或本次只精对某些岗位，不改变其他作品的支持范围。
